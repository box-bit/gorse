## Task 1 - Stakeholder, GQM, and Code Smell Selection

**Selected stakeholder and exact fictional concern from handout:** Scenario A - Alex, Software Maintainer: *"Our software keeps evolving. Future contributors need to understand and modify its components, but certain design choices might make that work unnecessarily difficult. Please investigate possible code smells, identify maintainability concerns worth addressing, and demonstrate a focused improvement without changing the software's intended behavior."*

**GQM goal:** Analyze **the `master` package of Gorse** for the purpose of **finding code smells that make future changes harder, and fixing one of them without changing behavior**, with respect to **maintainability (how easily a future contributor can understand and modify the code)**, from the viewpoint of **Alex, the software maintainer**, in the context of **Gorse v0.5.11 on the `semester-investigation` branch of the `box-bit/gorse` fork, analyzed with static analysis tools run in GitHub Actions**.

| Initial question | Question wording | Relevant metric(s) / observation(s) | Why useful? |
|---|---|---|---|
| **Q1** | Which functions in the `master` package are the hardest to understand and change, and why? | Cyclomatic and cognitive complexity per function; function length (lines/statements); nesting depth; duplicated code blocks; number of commits that changed each file in the last 12 months (churn); manual reading of the flagged code | Shows *where* the problems are. | Smell type | Why relevant to our GQM? | How we plan to investigate it (tool/rule/metric/inspection) |
|---|---|---|
| 1. **Long Method** — *In Go:* a long function or method (`func (m *Master) ...`), with many statements, branches and nested `if`/`for`/`switch` blocks. | A long function does many things at once. **Answers to the original GQM questions:**

- **Q1:** The hardest function to understand and change in the `master` package is `LoadDataFromDatabase` (`master/tasks.go`). It stands out on every measurement: 171 statements, cyclomatic complexity 84 and cognitive complexity 224 (the next highest are 88 statements for `loadDataset` and cognitive complexity 97 for `Restore`), 9 parameters (the only `argument-limit` finding), and duplicated code. It is also in the file that changes most often (48 commits in 12 months). Reading the source explains *why* it is hard: one function does 6 different steps, repeats the same logic for users and items, and shares many local variables between steps. Other areas are flagged too (`importExport*` handlers, `Restore`, `dump` in `rest.go`; the `Master` struct with 27 fields and 59 methods), but reading the code showed that the numbers do not always match the real difficulty: the `importExport*` handlers have high cognitive complexity mostly because of flat Go error handling, and `dupl` misses near-duplicates (in C1 steps 3-5 and in C2). So the answer comes from combining the tool results, the change history and manual inspection, not from the warning count alone.
- **Q2:** For the selected issue, **yes, partly.** The label rule was written twice and is now written once, in `labelIndexer.add`, with a name and a comment that explain it: a future change to the rule is made in **1 place instead of 2**, and users and items can no longer drift apart. The tool confirms that this duplication is gone (`dupl` 8 -> 6, the target pair removed, 0 new findings in the package), and `LoadDataFromDatabase` became smaller (467 -> 407 lines, 171 -> 139 statements, cyclomatic 84 -> 74, cognitive 224 -> 188). However, the function is **still** a Long Method with a Long Parameter List, so it is easier to change in one specific way, not easy to understand as a whole. On behavior: all 46 `master` tests pass before and after on GitHub, including the new characterization test, which checks exactly the part the refactoring touched (which labels each user/item gets, including the "add back to the first one" step). This is strong evidence, but not proof, that the behavior is unchanged.

**Conclusion and limits:** We found a real, verified duplication in the most problematic function of the package and removed it with a small Extract Method refactoring, without changing behavior as far as the tests can show. **What improved:** one copy of the label rule instead of two; a shorter and less complex `LoadDataFromDatabase`; 2 fewer `dupl` findings; a new test that protects the label logic (before, a broken "add back" step was not detected by any test). **What stayed the same:** all other 56 findings; the Long Parameter List (9 parameters); the function is still far above every Long Method threshold; the `importExport*` handlers and the `Master` struct (deferred). **Nothing got worse** in the measurements, but part of the complexity was *moved* into `labelIndexer.add` rather than removed, so the lower numbers of `LoadDataFromDatabase` overstate the gain for the package as a whole. **What we cannot claim:** (1) maintainability itself was not measured: the metrics are proxies, and we did not observe real contributors making changes; (2) the thresholds in `.golangci-lab6.yml` are our choice, other thresholds would give other counts; (3) the churn numbers are per file, not per function; (4) the tests use SQLite, small data and one order of users/items, so behavior with other databases or large, concurrent loads is not verified by our checks; (5) the analysis covers only the non-test code of the `master` package, so we make no claims about other packages.
